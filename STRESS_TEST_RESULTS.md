# Stress Test Results: Project 23 on Minikube

Branch `integrate/upstream-k8s` at commit `70161e1`, tested 27 Nov 2026. The stack was deployed with the Ansible playbook, verified, run through the Playwright suite, load tested with k6 (ramp and spike), and put through three disruption tests: deleting an API pod, deleting the database pod, and a rolling update. No application code or manifests were changed during testing.

**Update after fixes.** Bugs B1 to B5, plus a keep-alive mismatch found while retesting (B7), are fixed on branch `fix/load-rollout-clipboard`. The ramp profile now runs at about 200 req/s with 0 failed requests, and the spike profile drops from 70.5% to 0% failed. See [section 7](#7-after-fixes). Sections 1 to 6 describe the original run on commit `70161e1`.

**Summary of the original run.** Deployment, service discovery, persistence and autoscaling all work. Under load the API fails often. Without a connection pool, Postgres rejects or times out new connections from about 50 concurrent users. On the spike profile, the readiness probe times out and the Ingress is left with no endpoints at all. About 22% of requests failed on the ramp profile and 70% on the spike profile.

## 5. Bugs found

### B1. API pods crash on startup when Postgres is not ready

**Severity:** low.

**Evidence:** On every fresh deploy, both API pods restarted once. `kubectl logs --previous` shows `psycopg.OperationalError: connection failed: ... Connection refused` and then `ERROR: Application startup failed. Exiting.` One `project23-b` pod also crashed this way during the rolling update under load.

**Cause:** `lifespan()` in `app.py` connects once with no retry. The playbook applies the database and API together, so the API often starts before Postgres accepts connections.

### B2. No connection pool, so Postgres is the bottleneck and refuses connections (NFR-6, the known risk)

**Severity:** high.

**Evidence:**
- Across the four ramp runs there were 1620 `FATAL: sorry, too many clients already` and 3519 `connection timeout expired` errors.
- All ramp-run 503s came from the app as `Database unavailable`.
- Failures begin around 50 VUs and only about 40 req/s get through.
- Even at 5 VUs, p50 is about 112 ms.

**Cause:** every request (including every `/health` probe) opens a new Postgres connection. Each one costs a backend process plus SCRAM authentication. Postgres used about 1.3 CPU cores. With 8 pods and up to about 40 worker threads each, the 97 non-reserved connection slots run out, and `connect_timeout=3` expires while Postgres is busy creating connections.

Scaling out the API makes this worse, not better: more pods mean more concurrent connection attempts against the same limit.

### B3. Readiness probe fails under load, and the Ingress loses every endpoint

**Severity:** high.

**Evidence:**
- In the spike run, 8528 of 8577 503s came from ingress-nginx itself, with no upstream address.
- The controller logged `Service "url-shortener/shortener-api" does not have any active Endpoint`.
- Ready API pods dropped to 1 and then 0.
- Pod events: `Readiness probe failed: ... context deadline exceeded (Client.Timeout exceeded while awaiting headers)`.

**Cause:** the handlers are synchronous, so they share uvicorn's thread pool (about 40 threads) with `/health`. At 300 VUs the pool is full, and the probe request waits longer than its 4 s timeout. Because `/health` also opens a database connection (B2), database slowness alone can mark a pod unready. Once every pod is unready, the Ingress can't send traffic to any of them.

### B4. Rolling update and scale-in drop in-flight connections (K8-9)

**Severity:** medium.

**Evidence:** 2 502s during the rolling update: `connect() failed (111: Connection refused) while connecting to upstream` to pods that were terminating.

The spike run also had 2 502s (13:37:36, both `POST /api/links` to pod 10.244.0.18). That pod was not terminating, so these have a different, unconfirmed cause: the pod was overloaded and briefly unready at the time.

**Cause:** the pod spec has no `preStop` delay. Uvicorn stops listening when it receives SIGTERM, before ingress-nginx has removed the pod from its upstream list.

### B5. Copy to clipboard does not work through the Ingress over HTTP (FR-6)

**Severity:** medium (user-facing).

**Evidence:** Playwright `ui.spec.js:30` fails on `http://shortener.test` with the status message `Select and copy the short link manually.` The same test passes on `http://localhost:8080`.

**Cause:** `frontend/main.jsx:41` calls `navigator.clipboard.writeText`. Browsers only provide that API on secure origins (HTTPS or localhost). EX-8 (TLS) or a fallback copy method would fix it.

### B6. HPA cannot react to short spikes on this cluster (environment, not app)

**Severity:** low.

**Evidence:**
- During the 80 s spike, the HPA CPU value stayed at a stale 51%.
- The first scale decision came at 13:38:22, after load had ended. The HPA then scaled to 8 with no traffic, and stayed there about 6.5 minutes.

**Cause:** minikube's metrics-server runs with `--metric-resolution=60s`, and the HPA treats unready pods as 0% CPU when deciding to scale up (B3 makes pods unready). Separately, pod startup CPU registers as load. Right after a manual scale to 4 with no traffic, the HPA read 588%.

### Differences from the PRD (not bugs on this branch, but checks that would fail as written)

| Item | PRD | This branch |
|---|---|---|
| Namespace | `shortener` | `url-shortener` |
| Database workload | StatefulSet and headless Service `postgres` | Deployment (Recreate), PVC, ClusterIP Service `db` |
| Configuration | ConfigMap for `DATABASE_URL` | Set inline in the Deployment |
| HPA | 2 to 6 replicas at 60% | 2 to 8 replicas at 65% |
| Ingress host | `short.local` | `shortener.test` |
| Ansible structure | Inventory, four roles, teardown | One playbook, no roles, no smoke test, no teardown |
| Resource limits | Requests and limits | Requests only |

Pods with no CPU limit can burst to 10 to 15 times their request (`kubectl top` showed up to 1182m per pod against a 100m request). This is why HPA utilization reads 1000% or more.

## 6. Reproduce

```sh
minikube start --cpus 4 --memory 4g
for a in storage-provisioner default-storageclass metrics-server ingress; do minikube addons enable $a; done
docker build -t url-shortener:project23 . && minikube image load url-shortener:project23
ansible-playbook -i localhost, ansible/deploy.yml -e kube_context=minikube -e app_image=url-shortener:project23
echo "$(minikube ip) shortener.test" | sudo tee -a /etc/hosts
(cd e2e && npm ci && npx playwright install chromium && BASE_URL=http://shortener.test npm test)
docker run --rm --network host -e TARGETS=http://$(minikube ip) -e HOST=shortener.test -e PROFILE=ramp \
  -i grafana/k6 run - < scripts/loadtest.js
```

For the spike test, run the same `docker run` with `PROFILE=spike`. Watch the autoscaler with `kubectl -n url-shortener get hpa -w`.

## 7. After fixes

Fixes on branch `fix/load-rollout-clipboard`, tested on the same minikube cluster with images `url-shortener:project23-c` (B1 to B5) and `url-shortener:project23-d` (adds B7).

### What changed

| Bug | Fix | Files |
|---|---|---|
| B1 startup crash | Schema setup retries for up to 30 s (`DB_STARTUP_TIMEOUT`) instead of exiting | `app.py` |
| B2 no connection pool | `psycopg_pool.ConnectionPool` per pod (max 10, `DB_POOL_MAX`; 10 s wait, `DB_POOL_TIMEOUT`). Connections are checked before use, and pool timeouts return 503. 8 replicas x 11 connections = 88, under the 97 available | `app.py`, `requirements.txt`, `k8s/api.yaml.j2` |
| B3 readiness probe | `/health` is async and uses its own one-connection async pool, so it never waits behind request threads | `app.py` |
| B4 rollout drops | `preStop` runs `sleep 5`, so pods keep serving while they are removed from endpoints | `k8s/api.yaml.j2` |
| B5 Copy over HTTP | Falls back to a hidden textarea and `execCommand('copy')` when the Clipboard API is unavailable. The UI test now checks the copied text on both paths | `frontend/main.jsx`, `e2e/tests/ui.spec.js` |
| B6 HPA lag | Environment only. The README documents lowering metrics-server resolution to 15 s | `README.md` |
| B7 keep-alive mismatch (new) | Uvicorn `--timeout-keep-alive 75`, longer than ingress-nginx's 60 s upstream keepalive. Before this, nginx occasionally reused a connection uvicorn had just closed and got `Connection reset by peer`; idempotent GETs were retried, POSTs returned 502 | `Dockerfile` |
